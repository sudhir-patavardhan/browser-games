How it works

The marketing system

Kreeda's marketing writes its own posts, buys its own ads and measures its own results — and publishes nothing until a human ticks a box. This page explains how those two facts live together: what the pieces are, where everything is stored, and what exactly happens when someone clicks merge.

Who does what

There are three kinds of participant, and the difference between them is the whole design. Agents propose. The Producer executes. The human decides.

CMO · a person Owns the brand and the budget. Approves every post and every ad by merging one pull request. Sets the spending ceilings. Answers what the system cannot decide alone.
Producer · code Never an LLM, never creative. Publishes approved posts, launches approved ads, enforces the spending ceilings, stops ads that are failing, retries what broke, and writes the log. If it is deterministic, it lives here.

Between them sit six Agents. An Agent is a role, not a program: a Claude session follows that role's prompt, and its output is accepted only if it validates against a schema. An Agent can only ever propose.

AnalystReads the whole funnel — impressions, clicks, sessions, people who actually played — and says what is working, with numbers attached.
StrategistWrites next week's plan: which game, which angle, which channel, which day, and why. Names where the ad money should go.
CreativeTurns a one-line brief into a finished post: the copy, the image card, the video. The only Agent that is a model call made by code rather than a session.
Media BuyerProposes an ad: game, angle, creative, targeting, budget. Proposes — it cannot spend.
Performance AnalystWrites the post-mortem when an ad ends: promised versus delivered, cost per player, and one thing to change.
Chief of StaffWrites the weekly briefing the CMO reads in two minutes: headline numbers, what worked, what the system decided, what still needs a human.

How approval works

This is the part worth understanding properly, because it is the safety mechanism the whole system rests on.

Every day, the Producer opens or updates one pull request. Its body is a checklist — one line per post waiting for a decision, one per proposed ad, each with the full text and a link to the exact image or video that would go out. Every line arrives pre-ticked.

Closing the pull request without merging changes nothing at all.

That is deliberate. Ignoring it is always safe — nothing is published by default, nothing is published on a timer, and there is no setting anywhere that turns approval off. A post nobody decides on simply expires after three days.

Where things are stored

Four places, each with one job. Keeping them apart is what stops a marketing run from rebuilding the website, and what stops an unrelated code change from rewinding live data.

WhereWhat lives thereWho writes it
main The games, this website, and the marketing system's code. No marketing data whatsoever. People, in pull requests
marketing-state Everything the system knows: the post queue, the ad ledger, metrics, the Agents' outputs, the run logs, the weekly briefing. An orphan branch — it shares no history with the code. The Producer, and only the Producer
marketing-review Nothing. It is one empty commit that exists so the pull request has something to merge. Approving is a decision, not a change to any file. The Producer
A GitHub release called media Every rendered video and image card. Not in git — a year of videos would add half a gigabyte to the repository. The Creative

The split matters for a specific reason. A video is rendered on one day, reviewed on another, and published on a third — possibly by a different machine. Because the file lives on a release rather than in a temporary folder, the file the CMO previews is byte-for-byte the file that goes out.

A post's life

Every post moves through the same states, and every move is checked. A state is never just assigned — an earlier version of this system did that, and published some things twice.

When it runs

The system has no server and no daemon. It wakes up on a schedule, does one job, and stops. Each run is a scheduled Claude session with a fixed instruction and a rule against improvising.

RunWhenWhat it does
Morning desk03:30 dailyThe Analyst reads yesterday. Finished ads get a post-mortem. If there is room under the budget, the Media Buyer proposes a new one.
Publish09:00, 13:00, 17:00The Producer alone. Read what was approved, expire what is stale, write anything due soon, publish what is ready, pull the numbers, update the pull request.
PlanningSundays, 16:00The Strategist writes next week. The Chief of Staff writes the briefing. Monday and Tuesday's posts are written and waiting before the evening is out.

All times UTC. Publishing three times a day rather than continuously means a post has a slot, and a slot that is missed is caught by the next one rather than lost.

Money

Paid promotion is deliberately small and deliberately hard to escalate. The ceilings are frozen in the code itself: $10 a day for any one ad, $25 a day across all of them. Configuration can lower those numbers and cannot raise them.

Every ad is a three-day trial that always ends. Nothing runs indefinitely and nothing is topped up. If an ad is doing well, that is recorded as a result, and the Media Buyer may propose a fresh, larger one — which goes back through the same pull request, and needs the same tick. An ad that is clearly failing is stopped a day early.

Launching is ordered so that a crash cannot cost money: the ad is created paused, written to the ledger immediately, given its targeting, and only switched on at the very last step. A failure at any point leaves something visible, paused, and unbilled.

How success is measured

Not impressions, and not clicks. The number that matters is Players: someone who reached thirty seconds of real, visible play on a game page. Everything else is a step on the way to that.

Every published link carries where it came from — the channel, whether it was paid, the category or ad, and the specific post. When a visitor plays, that fact is recorded against those markers. So the question "did that Tuesday post about Carrom actually bring anyone who played?" has a real answer, and the Analyst uses it to decide what next week looks like.

Why build it this way?

An agent that can publish is an agent that can embarrass you at 3am. An agent that can spend is one that can spend all of it. So the parts that need judgement are separated from the parts that touch the outside world, and everything that touches the outside world waits behind one box that a person has to tick.

The system is open source, and the design decisions — including the ones that were tried and rejected — are written down alongside the code. Read it on GitHub.
